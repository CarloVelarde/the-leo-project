## A packet’s journey (story form)

Suppose you are on a video call.

1. **Your app** generates media; the OS/network stack packetizes it (Module 1).  
2. Packets leave via Wi‑Fi/Ethernet to your **Starlink-class terminal**.  
3. The terminal’s **phased array** maintains a beam to a **serving satellite** above min elevation (Module 6).  
4. The satellite either:  
   - sends traffic to a **gateway** with fiber into the Internet, or  
   - forwards via **optical ISLs** across the constellation toward a better exit (Module 7).  
5. Terrestrial routers deliver packets to the other participant’s network (Module 1 again).  
6. Return traffic reverses the path — possibly on different sats/gateways milliseconds later.  
7. Meanwhile, your serving satellite is racing toward the horizon; the system **hands over** to the next bird so the call continues (Module 6).

That entire loop must usually complete fast enough that RTT stays in a comfortable interactive band — the design goal contrasting with GEO’s multi-hundred-millisecond light-time tax (Module 2; <InlineSource id="starlinkTech" />).

## Performance: what “latency” is made of

When people say “Starlink latency,” they mix several contributions:

| Ingredient | What it is |
|------------|------------|
| **Propagation** | Speed-of-light time on radio/laser/fiber legs |
| **Processing** | Modems, coding, encryption, scheduling |
| **Queueing** | Waiting behind other traffic (congestion) |
| **Routing path length** | Extra ISL hops or hairpin gateway choices |
| **Handover transients** | Brief disruptions or path changes during switches |
| **Terrestrial tail** | Everything after the gateway |

LEO primarily attacks **propagation to/from the space segment** vs GEO. The rest is still classic networking (<InlineSource id="mdnLatency" />, <InlineSource id="hpbnLatency" />).

## Handovers in practice (continuity)

From a user’s perspective, success looks like: apps keep working while the attachment point changes. That requires:

- overlapping coverage so a next sat is ready,  
- coordinated scheduling between terminal and network,  
- and backhaul paths that remain valid after the switch.

Mobility (vehicles, ships, aircraft) adds motion on *both* sides: the terminal moves and the sky moves. The algorithmic problem gets harder, but the conceptual model stays the same.

## The algorithm layer (problem names, not secret recipes)

Without reverse-engineering any operator, mega-constellation networking faces known problem classes:

1. **Satellite selection** — which sat should serve this user now? (elevation, load, predicted remaining visibility)  
2. **Beam / resource scheduling** — who gets which spectrum/time/beam resources?  
3. **Routing on a dynamic graph** — which ISL/gateway path for this traffic class?  
4. **Handover planning** — when to switch to minimize disruption?  
5. **Constellation maintenance** — station-keeping and collision avoidance (Module 4) as the geometry substrate.

Research papers measure latency distributions, reconfiguration timescales, and routing strategies under public assumptions; treat them as *further reading*, not as ground truth for any vendor’s live policy.
